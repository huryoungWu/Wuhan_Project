# README — 数据清洗与效率预测设计说明

> 对应代码：`train.py`
> 数据流：`merged_minute_all.csv`（秒级原始合并数据，约 4 GB，文件名沿袭旧版命名）→ 逐步清洗 → `processed_cache.parquet` 缓存 → 训练

## 第一部分：数据清洗逻辑（按代码执行顺序）

### 0. 预处理缓存机制

首次运行完成全部清洗后保存为 `new_data/processed_cache.parquet`（清洗后 2,449,797 行），并写入 `_cache_version = 'power_diff_v2'` 标记列。下次运行时**仅当**同时满足：

- 存在 `170:总管压力_修正` 列（压力修正已做过）
- `_cache_version` 列全部等于 `power_diff_v2`（功率口径为分钟级差分，见 3.4）

才直接复用缓存，否则从 CSV 全量重跑清洗。这样清洗代码的改动（阈值、新规则）会自动触发重建，不会静默使用过期数据。

### 1. 压力修正（`correct_pressure`，清洗前执行）

```
修正后压力 = 原压力 − (吸水井液位 − 3.58) / 102   (MPa)
```

- 吸水井液位读取自原始列 `170:吸水井液位`（m），修正量 = (液位 − 3.58)/102，即液位每升高 1 m，压力减少约 0.0098 MPa（静水压头换算）。
- 液位缺失的行按修正量 = 0 处理；**修正后的压力覆盖 `170:总管压力` 参与后续清洗与训练，液位本身不进入模型特征**（训练时只有液位的修正效果，不依赖液位绝对读数的准确标定）。
- 修正结果同时写入 `170:总管压力_修正` 列，作为缓存校验标记。

### 2. 行级清洗（主函数内，严格按以下顺序执行）

| # | 规则 | 条件 | 目的 |
|---|------|------|------|
| 1 | 传感器全 NaN 行 | 除 `F_TimeStamp/F_DateTime/flowtotal/LJflowtotal` 外所有列全为 NaN | 剔除整行无读数的空记录 |
| 2 | 管2极端野点 | `170:2_瞬时流量 > 10000` | 传感器溢出/记录错误（正常量级 ~1000） |
| 3 | 管1极端野点 | `170:1_瞬时流量 > 10000` | 同上 |
| 4 | 频率超范围 | 任一 `运行频率 > 55 Hz` | 变频器不可能输出 >55Hz，超范围读数不可信 |
| 5 | 总管压力异常 | `170:总管压力 < 0.1` 或 `> 0.5 MPa` | 物理不可达区间（水厂扬程 ~0.3–0.45 MPa） |
| 6 | 全泵停止 | 7 个泵运行状态全为 0 | 无运行泵的样本对"运行工况"无意义，且流量/效率均为 0 |
| 7 | 泵7停但管3有流量 | `70:7_泵运行 = 0` 且 `70:3_瞬时流量 > 10` | 物理矛盾（管3只由泵7供水），先粗剔除 |
| 8 | 管1流量 3σ 离群 | 泵1运行时 `170:1_瞬时流量` 超出 μ±3σ | 消除传感器偶发大偏差点；仅在泵1运行时统计，避免全停 0 值污染分布 |
| 9 | 幽灵流量（主泵组） | 泵1~6 全停 但 管1/管2 流量 > 5 | 主泵全停时管1/管2不应有水，残余读数为幽灵流量 |
| 10 | 幽灵流量（泵7） | 泵7停 但 管3 流量 > 5 | 与 #7 同族但阈值更严（>5 而非 >10），成对保留作为分层清洗 |
| 11 | 流量突变 | 按时间排序后相邻秒差分绝对值 > 500 m³/h，删除跳变行**及其后一行** | 传感器跳变是"跳上去再跳回来"成对出现，删两行才清干净 |
| 12 | 关键列 NaN | 3 个流量列、7 个泵状态列、7 个频率列、总管压力任一为 NaN | 训练必需列不允许缺失 |

**汇总输出**：打印清洗前后行数与剔除百分比，用于人工核对每次口径变化的影响。

### 3. 功率计算（供效率标签用）

> 数据实际时间粒度：**1 秒**（缓存 244.9 万行，跨度 2026-06-11 ~ 2026-07-16 约 35 天，相邻行间隔 99% 为 1 s）。

#### 3.1 为什么用累计电度差分（而非电流×电压）

现场有两类功率数据源：

| 数据源 | 说明 | 问题 |
|--------|------|------|
| A. 电流×电压瞬时计算 | 172:1~6 三相电压/电流采样值直接相乘 | **不准确**：瞬时采样受电磁干扰与量程噪声影响；电流互感器二次侧折算误差大；乘积未计功率因数与谐波，系统性偏离真实有功功率；泵7 无电压电流数据 |
| B. 累计电度表 ★当前口径 | 172:1~6_泵电度（累计 kWh） | **准确但需差分**：电度表为计量级仪表（用于电能结算），精度远高于瞬时采样；但读数是从不清零的累计值，必须差分才能得到功率，且 0.25 kWh 分度的跳字特性带来一系列问题（见 3.3） |

效率是"有功功率之比"，必须用真实有功功率（路径 B），电流×电压的计算值（路径 A）仅作参考。

#### 3.2 电流×电压计算功率（`compute_pump_powers`，已弃用）

早期版本用三相电压/电流采样值计算单泵功率：泵1~6 为 `(V_A·I_A + V_B·I_B + V_C·I_C) / 1000`，泵7 为 `70:7_总有功 / 1000`。
由于电流电压采样本身不准确（互感器误差、未计功率因数、瞬时噪声、泵7 缺数据），该口径**当前仅用于数据质量统计与打印，不参与效率计算**（见 3.6）。

#### 3.3 累计值为什么不能直接差分（跳字/量化问题，`power_diff_v2` 修复前）

电度表按 **0.25 kWh 分度**：只有累计电量满 0.25 kWh 才"跳一个字"，读数不是实时连续值。直接对累计值差分时，结果取决于"这一秒有没有跳字"，而不是真实功率：

```
跳字瞬间: ΔkWh / Δt = 0.25 kWh / (1/3600 h) ≈ 900 kW 虚假脉冲
未跳字秒: ΔkWh = 0 → 功率 0（真实功率并非 0，只是没到最小分度）
```

假脉冲被 clip 到 500 kW 后，又被 ffill 填满跳字间隙（下一跳到来前一直沿用 500），
导致总功率**系统性虚高约 2.7 倍**——不是偶发毛刺，而是整体偏高；该口径下效率标签被系统性压低（已由历史训练实测验证）。

累计值本身的固有问题（也是后续处理要逐条解决的）：

1. **分度量化**：最小分度 0.25 kWh，任何瞬时差分都带 ±0.25 kWh 的量化误差；功率越低跳字越慢，量化噪声占比越大（30 kW 泵约 30 s 才跳一次，秒级差分几乎全是 0）；
2. **"未跳字 ≠ 功率为 0"**：差分结果为 0 无法区分"泵停止"（真实 0）与"泵运行但未跳字"（信息缺失），必须借助泵运行状态列区分；
3. **只增不减、依赖时间顺序**：累计值单调递增、从不清零，差分必须先按时间排序；数据断点/缺行时若按固定时间间隔计算会算错，需用真实时间戳差；
4. **低功率信息被量化噪声淹没**：秒级差分在"跳字节奏"面前完全失效，必须放大差分窗口才能恢复功率信息（见 3.4）。

#### 3.4 分钟级差分：累计电度 → 有功功率（当前口径，`_pump_power_from_meter`）

核心思想：**把差分窗口从 1 s 放大到 1 min**。分钟窗口内无论电表跳 0 次还是 5 次，"分钟电量 ÷ 1 分钟"都是稳定功率；分钟功率最小分辨率 = 0.25 kWh/min = **15 kW**（量化噪声上限，300 kW 泵的分钟误差 ≤ ±5%）。

对每台泵（泵1~6）依次执行：

```
1. 分钟聚合
     kwh_min   = 每分钟取电度读数末值 last()   ← 累计表读数必须取末值（均值无物理意义）
     state_min = 每分钟泵运行状态取最大值 max() ← 分钟内任一秒运行即视为该分钟运行
2. 真实时间差
     dt_h = 相邻分钟读数的时间戳差分（秒→小时） ← 用真实间隔而非固定 1/60，天然容忍缺分钟/数据断点
3. 分钟功率
     P = ΔkWh / Δh，clip 到 [0, 500 kW]
     （500 kW 上限 = 额定 220 kW 泵的 2 倍余量 + 仪表裕度，拦截故障大脉冲）
4. 无跳字分钟（P == 0）且泵在运行 → 置 NaN，ffill(limit=30) 沿用上一分钟功率
     （bfill(30) 覆盖数据段开头尚无有效功率的窗口；30 分钟上限覆盖低功率泵的慢跳字节奏）
5. 泵停止的分钟 → 功率强制为 0（真实停机，不填充）
6. 回到秒级轴
     reindex(秒轴, method='ffill')：该分钟功率铺满整分钟
     泵停止的秒再强制 0（停机瞬间功率立即归零）
```

关键取舍：

- **用 last() 而非 mean() 聚合累计表**——累计值只有末值有物理意义，均值会把跳字节奏抹进读数；
- **停机不填充**——"无读数"在停机时是真实功率 0、在运行时才是缺失，两者必须区分，否则停机段会残留上一条运行功率；
- **15 kW 量化分辨率**——由电表分度决定（0.25 kWh/min），秒级滚动平滑（3.5）再压低一档；
- **分钟差分天然免疫跳字节奏**——分钟电量不依赖"这一分钟跳了几次"，只依赖总电量增量。

#### 3.5 总功率合成与平滑（`compute_total_power_from_meters`）

- 泵1~6：各自的 `_pump_power_from_meter` 秒级结果；泵7：`70:7_总有功` W → kW，clip [0, 200]（额定 90 kW 的 2.2 倍裕量；泵7 无电度表，只有瞬时有功表，不做差分）。
- 原始总功率 = Σ泵1~6 + 泵7，再经两级处理：

```
1. 总功率层 0 值 → ffill(limit=15)
   （泵级已处理，但整分钟所有泵都不跳字时总功率仍可能为 0；沿用最近 15 条有效值）
2. rolling(window=5, center=True, min_periods=1) 滚动均值
   （中心平滑：削掉差分量化产生的 ±15 kW 毛刺；min_periods=1 保证窗口两端不产生 NaN）
3. 剩余 NaN → 0
```

#### 3.6 单泵 V·I 功率的现状（`clean_pump_power` 清洗对象）

泵1~6 的电流×电压计算功率列仍被计算并做三段清洗（运行但功率≤0、高频低功率、频率分段 MAD，见第 5 节），但**已不参与效率计算与训练**——其输出仅用于打印泵功率统计表（人工核查数据质量）与历史兼容。

#### 3.7 理论功率（相似定律，PINN 基准）

```
P_theory = Σ 运行泵额定功率 × (f/50)³     (kW)
```

由泵额定参数直接计算，作为效率标签的物理校验基准：PINN 的"功率一致"约束要求**效率反推电功率 ≈ P_theory**（下限 0.33×、上限 1.5×1.15），可识别"流量/效率标签本身不合理"的样本（如效率 90% 而理论功率仅 30 kW 的矛盾）。

### 4. 效率标签计算（`compute_efficiency`）

```
总流量 = 管1 + 管2 + 管3 (各自 fillna 0)
水力功率 = 9.81 × 总流量 × 压力 × 102 / 3600   (kW)
总管效率 = 水力功率 / 总有功功率 × 100,  clip 到 [0, 90]
```

- `×102/3600`：MPa → 米水柱，m³/h → kg/s 的单位换算（9.81·Q·H/3600）。
- clip [0, 90]：物理上效率不可能为负或 >90%，极端读数（如停机瞬间功率分母≈0）被限幅。
- 同时计算 `总管效率_valid` 标记：**总流量 > 100 且 总有功功率 > 30 kW** 的行才视为效率有效样本。
- 训练标签实际使用 `总管效率_pct`（clip 后全列），`_valid` 列保留用于后续统计分析。

### 5. 单泵功率清洗（`clean_pump_power`，频率分段 MAD）

对泵1~6 功率列依次做三段清洗，被标记的行功率置 NaN，最后统一 `dropna` 删整行：

1. **运行但功率 ≤ 0**：频率 > 0 且功率 ≤ 0 → 删除（变频泵不可能零功耗运行）
2. **高频低功率**：频率 > 20 Hz 且功率 < 泵平均功率的 5% → 删除（高频必有大功率，读数矛盾）
3. **频率分段 MAD 离群**：频率四舍五入取整分箱，箱内样本 ≥ 20 且 MAD ≥ 1e-9 时，`|x − med| / MAD > 3.5` 判为离群 → 删除（主函数调用阈值 3.5，默认 5.0）

> 注：v6 版本训练特征与标签**均不再使用**这些单泵功率列（总功率口径已改为电度差分），此步骤保留主要是为了输出泵功率统计表供人工核查数据质量。

### 6. 训练/测试划分（按泵组组合，防数据串扰）

```
泵组状态 = 7 位 0/1 串（7 个泵的开关状态拼接）
样本数 < 100 的组合 → 归入训练集（样本太少无法有效评估）
剩余有效组合随机 80% 训练 / 20% 测试（USE_FIXED_SEED=False，每次运行随机）
验证：测试集组合绝不出现于训练集（否则打印警告）
```

- 清洗后共 39 个训练组合 + 8 个测试组合（见 `results/metrics_result_*.txt` 头部）。
- 这个划分是关键设计：泵组组合相同的数据工况完全相同，若同一组合既进训练又进测试，模型"背答案"（记住该组合的映射而非学习物理规律），评估会虚高。
- `TRAIN_SAMPLE_SIZE = None`：默认全量训练不采样。

### 7. 训练内处理（`train_model`）

| 步骤 | 处理 |
|------|------|
| 离散列二值化 | 泵运行状态 > 0 → 1 |
| 缺失兜底 | 连续特征与标签 `nan_to_num(0)`（posinf/neginf 一并归 0） |
| 标准化 | 连续特征与输出各自 `StandardScaler`（fit on train, transform on test） |
| 数值保护 | `scale_ < 1e-4` 的特征用 1e-4 兜底，防止除零/Inf |
| 训练 | Adam lr=1e-3 + weight_decay=1e-4，ReduceLROnPlateau，早停 patience=60，梯度裁剪 max_norm=1.0，AMP |
| 评估后处理 | 预测先 clip 到 [-50, 50]（标准化空间）再反标准化；物理 clip：流量 ≥ 0、效率 ∈ [0, 100] |
| MAPE 口径 | 仅对 `y_true > 10` 的样本计算（避免除以小真值的爆炸） |

### 8. PINN 物理约束（训练损失的一部分，`physics_loss_pump`）

基于水泵相似定律（Q∝f、H∝f²、P∝f³），把物理规律作为软约束加入损失：

| 约束 | 表达式 | 权重 |
|------|--------|------|
| 幽灵流量 | 泵1~6全停 → 管1/管2 流量=0；泵7停 → 管3=0 | 0.01 |
| 流量上界 | 总管流量 ≤ 1.15 × Σ(运行泵额定流量×(f/50)) | 0.01 |
| 功率一致 | 效率反推电功率 ≈ Σ(运行泵额定功率×(f/50)³)，允许 ±15%/×1.5 | 1e-4 |
| 扬程上界 | 系统扬程 ≤ 1.15×1.2×运行泵最大理论扬程 | 0.05 |

额定参数（Q/P/H, f=50Hz）：P1 2020/220/32、P2 670/132/43、P3 2020/220/32、P4 1260/220/43、P5 670/132/43、P6 1260/220/43、P7 670/90/33。

## 第二部分：为什么直接预测效率、跳过功率预测

v6 版模型输出 4 维：`[170:1流量, 170:2流量, 70:3流量, 总管效率]`，**刻意移除了功率预测**。理由如下：

### 1. 功率数据质量差，是错误的主要来源

- 电度表 0.25 kWh 分度、约 5 秒跳一次 → 秒级差分会制造 900 kW 的虚假脉冲，总功率**虚高约 2.7 倍**（历史实测问题，已通过分钟级差分修复，见第一部分 3.3）。
- 即使修复后仍有残余噪声：分钟无跳字只能靠 ffill 沿用上一分钟（最多 30 分钟），量化误差 ±0.25 kWh/分钟 ≈ ±15 kW 依然存在。
- 泵级电流×电压乘积功率未计功率因数、受互感器与采样噪声影响，本身就有系统偏差。
- 一句话：**功率的标签噪声远大于流量**。让模型去拟合一个噪声很大的量，只会浪费网络容量、拉低整体精度。

### 2. 避免误差的除法放大（数值稳定性）

如果走"先预测功率 → 再算效率"的老路：

```
效率 = 水力功率 / 电功率
```

- 电功率预测相对误差 10% → 效率误差至少 10%，且方向随机；
- 电功率预测接近 0 时（停机/低负荷），除法直接爆炸，只能靠 clip [0,90] 硬截断，数值不稳、梯度也不稳。

**直接预测效率**则让网络学习"水力功率/电功率"这个比值本身——比值的变化范围小（正常运行 3~8%）、更平滑、更稳定，远比预测分母（功率，0~500 kW 大动态范围）好拟合。实测效率 MAE ≈ 2.14%、RMSE ≈ 2.74%，说明该量是可学的。

### 3. 效率是功率链上"最难物理推导"的量，功率不是

- 泵功率有成熟的物理解析近似：相似定律 `P ∝ f³` + 额定参数即可估算（PINN 的功率一致约束用的就是它），**不需要用神经网络学**。
- 效率则受工况点、泵磨损、汽蚀、组合运行干扰等因素影响，**没有解析公式**，只能从数据中学——这正是神经网络的用武之地。
- 设计原则：把网络容量花在物理上最难算的量（效率、流量），把容易算的量（功率≈相似定律）留给公式。物尽其用。

### 4. 功率可"免费"反推，不损失信息

有了流量预测 Q 和效率预测 η，功率可以直接推导：

```
水力功率 Ph = 9.81 × Q_total × H × 102 / 3600     (H = 输入压力，Q_total = 3管流量之和)
电功率 P   = Ph / η
```

也就是说 **跳过功率预测 ≠ 拿不到功率**，只是把功率从"预测输出"降级为"推导结果"。推导路径反而更准：它复用了精度最高的流量预测，而非让网络额外学习一个有噪声的中间量。推理端 `pump_inference.py` 与优化脚本（`pump_optimize_PSO.py` 等）正是这样通过 流量+效率 反推功率来计算能耗的。

### 5. 输出维度缩减，容量聚焦

- 老版 5 维输出（3流量 + 功率 + 效率）→ v6 版 4 维（3流量 + 效率）。省下的容量全部用于流量与效率，二者精度都受益。
- 多任务头从 3 个减为 2 个（170 系统头 + 70:3 专用头 + 效率头，原本还有功率头），训练更稳。

### 6. 与业务目标一致

最终业务是泵组优化（`pump_optimize_PSO.py`）：给定需求流量，寻优目标本质是**最小化电功率（或最大化效率）**。优化器需要的是"给定工况 → 效率/能耗"的映射。直接以效率为输出：

- 与优化目标一致，优化结果直接可解释；
- 若输出功率，优化时还要二次求导/除法换算成效率，误差放大且数值不稳。
